# Day14 深度指南 - bring-up checklist 方法论

## 一、Day14 是什么？

Day14 是 W2（嵌入式驱动模式）的最后一天，定位是**bring-up checklist 方法论沉淀**。

**核心目标**：把 day08-day13 积累的驱动开发经验，凝练成一张可复用的 bring-up checklist，让"拿到新寄存器表后怎么推进联调"变得有章可循。

Day14 不写新驱动。它的重点是：
1. **方法论沉淀**：把联调经验变成 checklist
2. **9 步推进节奏**：从读寄存器表到完整数据路径
3. **8 个卡点预判**：提前知道哪里会卡
4. **3 轮验证模板**：最小安全访问 → 初始化顺序 → 功能链路

## 三、bring-up checklist 核心框架

### 3.1 为什么要用 checklist？

```
不用 checklist 的问题：
  - 拿到寄存器表后不知道先做什么
  - 一次想做太多（probe + IRQ + DMA 一起上）
  - 卡住了不知道哪里卡
  - 每次联调都是"试错-修bug"的无效循环

用 checklist 的价值：
  - 把复杂联调拆成 9 个阶段
  - 每个阶段有明确的"最低产出"
  - 8 个卡点提前预判，不重蹈覆辙
  - 3 轮验证模板确保"最小安全访问优先"
```

### 3.2 9 步推进节奏

├─────────────────────────────────────────────────────────────────────┤

│  产出：寄存器地图草图（控制/状态/中断/数据/调试 分组）               │
│                                                                      │

## 四、输入物准备

### 4.1 六类输入物

```
拿到寄存器表后，先收齐以下六类输入物，再开始联调：

1. 寄存器表/芯片手册
   - 基地址、偏移、位定义、复位值、访问属性（RO/RW/W1C 等）

2. 上电/时钟/reset/电源域说明
   - 时钟树结构、reset 顺序、电源域依赖

3. 中断说明
   - 中断号、触发类型、状态位、清中断方式

4. 数据路径说明
   - PIO / FIFO / DMA / doorbell / descriptor 等

5. Linux 侧资源信息
   - DT reg / interrupts / clocks / resets / power-domains

6. 最小验收目标
   - 先跑通"读版本寄存器"还是"中断计数"还是"收发一包数据"
```

### 4.2 为什么输入物必须先收齐？

```
输入物不完整的风险：
  - 没有时钟/reset 说明 → 寄存器读值全 0 或全 1
  - 没有中断说明 → 不知道 status 位怎么清
  - 没有数据路径说明 → 以为用 PIO 实际要用 DMA
  - 没有 Linux 侧 DT 信息 → ioremap 地址和实际不符

Day14 的原则：
  "磨刀不误砍柴工" —— 输入物不全不开始联调
```

## 五、8 个最常见的卡点

### 5.1 卡点详解

```
1. 基地址错
   现象：DT reg 看起来对，但实际 IP 映射窗口不对
   原因：IP 映射窗口和 DT 地址不一致、bus address vs phys address 混淆
   预防：先读 ID/VERSION 寄存器验证地址正确性

2. 依赖没开
   现象：寄存器读值异常（全 0、全 1 或总线异常）
   原因：clock/reset/power-domain 没 ready
   预防：第3步确认依赖条件，第2步只读不写验证

3. 访问语义理解错
   现象：越调越乱，状态位清了又来
   原因：把 W1C 当普通 RW 写
   预防：第4步明确访问语义，列出危险寄存器清单

4. 初始化顺序错
   现象：模块假死，中断不触发
   原因：还没 clear pending 就 enable interrupt
   预防：第6步单独列初始化顺序，第7步先清 pending 再 enable

5. 状态位没有真正清掉
   现象：中断一直来，状态位读出来一直是 1
   原因：write 了，但缺少 read-back 或写错 clear 位
   预防：第5步先做只读观测，验证写入后 read-back 符合预期

6. 跨层信息不一致
   现象：手册说一套，FPGA 文档说一套，驱动头文件又是另一套
   原因：多个信息源之间有历史版本差异
   预防：第1步读表时标注不一致处，第9步留证据

7. 一次想做太多
   现象：probe + IRQ + DMA 一起上，定位困难
   原因：没有按阶段拆分，"最小安全访问"原则没守住
   预防：3 轮验证模板，按顺序推进

8. 没有证据链
   现象：只说"寄存器不对"，但没有 dmesg / dump / trace 截图
   原因：没有养成留证据的习惯
   预防：第9步强制留证据，dmesg + 寄存器快照 + trace
```

### 5.2 卡点与步骤的对应关系

```
┌─────────────────────────────────────────────────────────────────────┐
│                    卡点 vs 步骤 对应表                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  卡点1（基地址错）         → 第1步（读表）、第2步（最小访问路径）   │
│  卡点2（依赖没开）         → 第3步（确认依赖条件）                  │
│  卡点3（访问语义理解错）   → 第4步（明确访问语义）                  │
│  卡点4（初始化顺序错）     → 第6步（初始化顺序）、第7步（中断联调） │
│  卡点5（状态位没真正清掉） → 第5步（只读观测）、第7步（中断联调）   │
│  卡点6（跨层信息不一致）   → 第1步（读表）、第9步（留证据）        │
│  卡点7（一次想做太多）     → 3 轮验证模板强制拆分                  │
│  卡点8（没有证据链）       → 第9步（每次联调都留证据）              │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

## 六、3 轮验证模板

### 6.1 第 1 轮：只证明"能安全访问"

```
目标：验证"基地址是否正确，寄存器是否可读"

检查项：
  - [ ] 资源解析成功（DT reg / platform_get_resource 正常）
  - [ ] ioremap 或 regmap 初始化成功
  - [ ] 读到 ID/VERSION 寄存器（返回非全0/非全1）
  - [ ] 读到 STATUS 寄存器
  - [ ] 导出一份 debugfs/proc 寄存器快照

最低产出：
  日志里能打印：基地址、版本号、默认状态值

这轮的核心原则：
  "只读不写" —— 任何写入操作都在第2轮以后
```

### 6.2 第 2 轮：只证明"初始化顺序正确"

```
目标：验证"依赖条件满足后，写入操作是否按预期生效"

检查项：
  - [ ] clock/reset/power-domain 顺序写清楚
  - [ ] 关键控制寄存器写入后 read-back 正常
  - [ ] 中断状态位可置位、可清除

最低产出：
  README 中一段"推荐初始化时序"

这轮的核心原则：
  "最小写入" —— 只写安全软配置位，不碰关键 enable 位
```

### 6.3 第 3 轮：只证明"一条功能链路成立"

```
目标：验证"完整功能路径是否通畅"

检查项（任选一条最短链）：
  - [ ] 一次 IRQ 路径可解释（status→mask→ack→handler）
  - [ ] 或一笔最小 PIO/FIFO 数据可走通
  - [ ] 或一次最小 DMA 描述符能完成

最低产出：
  单独的 data path TODO，不和最小 bring-up 混在一起

这轮的核心原则：
  "一条链" —— 不做完整数据面，只做"最短功能路径"证明
```

## 七、Day14 与 W3 的关系

### 7.1 W3 实验链路

```
Day14 的 checklist 方法论在 W3 中的应用：

W3 实验链路：
  arm64 + QEMU virt + BusyBox initramfs + demo_regmap + tracing/perf

Day14 checklist 应用：
  1. 先读表：QEMU virt 的寄存器映射表在哪里？
  2. 最小访问路径：demo_regmap 的 regmap 访问是否正常？
  3. 确认依赖：clock/reset/power-domain 在 QEMU virt 中怎么模拟？
  4. 访问语义：demo_regmap 的 W1C 寄存器怎么处理？
  5. 只读观测：snapshot 节点的只读路径是否正常？
  6. 初始化顺序：insmod → probe → regmap_init → 访问寄存器的顺序
  7. 中断联调：function_graph tracer 看 IRQ handler 路径
  8. 数据路径：demo_regmap 的 trigger 写路径
  9. 留证据：records 目录下保存 dmesg / trace / metrics.env
```

### 7.2 Day14 是 W2 的"方法论总结"

```
Day13：回答"已有驱动链路怎么测"
Day14：回答"拿到新芯片/新场景怎么推进联调"

Day13 是"测试"，Day14 是"方法论"

Day14 的 checklist 可以复用于：
  - W3 的内核裁剪实验（验证裁剪后主链路是否完好）
  - W4 的 PCIe 联调（IVSHMEM 寄存器 bring-up）
  - W5 的 DMA 调试（EDU device 寄存器 bring-up）
  - 以后工作中拿到真实芯片手册的实际联调
```

## 八、一句话原则

```
拿到寄存器表后，先做"最小安全访问 + 初始化顺序确认 + 证据留存"，
再做 IRQ、DMA 和完整数据路径。不要一上来把所有功能一起 bring-up。
```
