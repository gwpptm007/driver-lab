# W1 一页复盘

## 1. 接口

W1 这一阶段覆盖了一个字符设备驱动从“最小可加载”到“可回归验证”的基础接口闭环：

- `open` / `release`
- `read` / `write`
- `ioctl`
- sysfs
- debugfs
- waitqueue
- workqueue

从用户态视角看，已经形成了三类使用方式：

1. 直接读写设备节点
2. 通过 `ioctl` 传控制命令
3. 通过 sysfs/debugfs 查看和调整运行状态

这让仓库不再只是一个单点 demo，而是有了“接口层次”。

---

## 2. 设计

W1 的设计目标不是做复杂业务，而是把字符设备驱动最常见的骨架搭完整。

核心设计思路：

- 用最小字符设备承载主线逻辑
- 用 `ioctl` 承载控制面
- 用 sysfs/debugfs 提供可观测性
- 用 waitqueue 模拟阻塞等待
- 用 workqueue 模拟异步处理
- 用脚本把加载、卸载、并发压测串成回归流程

Day06 的 driver 采用的是“单槽 pending work + 单槽 output buffer”模型。这个设计简单、容易讲清楚，也适合初学阶段理解并发竞争、`-EBUSY`、阻塞读和结果唤醒之间的关系。

---

## 3. 风险

W1 已经暴露出几个很典型的驱动学习风险点：

### 1. 环境风险

不是所有问题都出在驱动代码本身。
Windows 的 Hyper-V、VMware 的嵌套虚拟化设置、Ubuntu 依赖包是否完整，都会直接影响实验体验。

### 2. 路径风险

如果 `build.sh` 写死个人目录，例如 `/home/wq7/workspace/...`，仓库一旦换机器或换目录就不容易复用。

### 3. 并发模型风险

当前 Day06 是单槽模型，因此高并发时大量 `-EBUSY` 是预期。这个模型适合教学，但不适合直接拿去承载多队列或高吞吐需求。

### 4. 卸载路径风险

只要引入 workqueue，就要认真处理模块卸载阶段的同步问题。`cancel_work_sync()` 之类的收尾动作不能漏。

### 5. 可观测性风险

如果没有 dmesg、debugfs、脚本统计和 README，很多问题会变成“感觉卡住了”，而不是“能被验证的问题”。

---

## 4. 回归

W1 最重要的成果之一，不是某个接口单独实现出来，而是形成了最小回归闭环：

- build.sh 一键启动实验环境
- `insmod/rmmod` 多次回归
- 并发读写压力测试
- dmesg 异常关键字扫描
- debugfs 状态核对

Day06 的正式结果已经证明：

- 500 次装卸可以完成
- 300 秒并发压测可以完成
- 无 Oops
- 无明显泄漏告警
- 模块可以正常卸载

这意味着 W1 已经不只是“能演示”，而是“能复跑、能验证、能解释”。

---

## 5. 小结

W1 的价值不是功能多，而是把基础套路走通：

- 有接口
- 有实现
- 有可观测性
- 有回归脚本
- 有环境说明
- 有复盘文档

这为后面的 W2 platform/DT/IRQ/regmap 打下了比较稳的基础。
