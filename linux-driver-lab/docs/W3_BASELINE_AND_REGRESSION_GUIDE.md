# W3 补充：基线、回归与交付衔接说明

## 1. 这份补充文档解决什么问题

`W3_REVIEW.md` 主要回答的是：

- W3 为什么要做
- D15 ~ D21 分别在做什么
- 为什么 W3 不是“新功能周”，而是“工程化收敛周”

但如果后面要继续进入 W4/W5，光有阶段复盘还不够，还需要一份更偏“交付衔接”的说明：

- W3 到底应该沉淀哪些可复用产物
- 哪些产物是 W4/W5 继续往前做时必须沿用的
- W3 的验收证据应该怎样组织，后面才能复用

这份文档就是补这个缺口。

---

## 2. W3 的真正产出，不只是 Day15 ~ Day21 目录

W3 最重要的成果，不是单个脚本，也不是单次测试通过，而是形成下面这套“后续还能继续用”的基础设施：

### 2.1 冻结基线

至少要冻结：

- 当前内核版本
- 当前架构与 QEMU 机器类型
- 当前 rootfs 组织方式
- 当前验证模块
- 当前启动命令
- 当前采样口径

如果这些内容不冻结，后面 W4/W5 的任何性能、体积、稳定性对比都会失去意义。

### 2.2 可重复采样

W3 不是“跑一次看看”，而是要把这些指标变成**可以重复采、可以横向比**的数据：

- 内核镜像大小
- rootfs 大小
- 启动时间
- 关键内存指标
- 模块数量
- `debugfs` / `ftrace` / `perf` 能否继续使用

### 2.3 自动回归

W3 的另一个关键点，是把“能不能启动、功能有没有坏”从主观判断，变成脚本化判断。

最小回归至少应该覆盖：

- guest 能正常启动到 shell
- 目标模块能加载
- 基础功能 smoke 能跑
- tracing/perf 能力没有被裁掉
- 关键日志中没有明显 error/oops/warn

### 2.4 结果可归档

W3 最后要形成一套后面还能引用的记录结构：

- `records/` 放原始证据
- `output/` 放整理结论
- `README.md` / `RESULTS.md` 放可读解释

这个组织方式非常重要，因为到了 W4/W5，你会继续复用同样的证据链思路。

## 3. W3 推荐沉淀的“必须保留项”

如果把 W3 看成 W4/W5 的前置平台，那么建议至少保留下列产物：

### 3.1 基线配置

建议保留：

- baseline `.config`
- config 片段或裁剪说明
- 关键启停项说明（tracing/perf/debugfs/module）

### 3.2 启动与打包脚本

建议保留：

- 内核构建脚本
- rootfs 打包脚本
- QEMU 启动脚本
- guest 内 `/init` 行为说明

### 3.3 profile / compare / verify 能力

建议保留：

- baseline 数据采集
- round2/分类裁剪采集
- 差异对比脚本
- 等价性检查脚本

### 3.4 tracing / perf 证据

建议保留：

- `available_tracers`
- `function_graph` 可用性
- `perf` 可用性
- 1 份最小 trace/perf 记录

这些内容对 W4/W5 很重要，因为后面你要继续写性能与稳定性报告。

## 4. W3 到 W4 的承接关系

很多人做到 W3 会有一个错觉：

> W3 做完了，后面要学 PCIe，好像可以完全断开重新来。

实际上可以独立开新目录，但**工程方法不应该断**。

W3 要继续带到 W4 的，不是具体 platform_driver 代码，而是下面这套方法：

### 4.1 先冻结实验场景

进入 W4 前，同样要先冻结：

- QEMU 设备模型
- guest rootfs 能力
- `lspci`/工具来源
- 内核 PCI / MSI 相关配置
- 记录口径

### 4.2 先留原始证据，再写总结

W4 里也一样：

- `lspci -vv`
- `dmesg`
- `/proc/interrupts`
- 用户态工具输出

都应该先落 `records/`，再写 `output/`。

### 4.3 继续保持“自动回归”思维

W4 不是“今天 probe 通了就算了”，而是应该延续 W3 的思路：

- 启动
- 加载
- 触发
- 查询
- 卸载
- 循环

最后脚本化。

## 5. W3 对 W5 的直接价值

W5 要做 bench / perf / ftrace / 稳定性报告，如果没有 W3，你很容易遇到三个问题：

### 5.1 没有对比口径

比如你测出了某个 bench 数据，但你并不知道：

- guest 配置是不是已经变了
- rootfs 工具是不是已经变了
- trace/perf 配置是不是已经变了

### 5.2 没有证据组织能力

W5 的产物不是“跑一个命令”，而是：

- bench 原始结果
- perf record/report
- function_graph 关键窗口
- 并发压测日志
- 1000 次循环统计
- 最终 1~2 页报告

如果没有 W3 的 records/output 思维，W5 很容易变乱。

### 5.3 没有回滚依据

W5 会开始做优化和对比。
如果没有 W3 形成的 baseline/compare 方法，优化前后很难讲清楚到底改善了什么、有没有副作用。

## 6. W3 建议这样验收，后面最省事

如果你要把 W3 作为真正能承接 W4/W5 的平台，建议验收至少包含：

### 6.1 平台基线

- baseline config 已冻结
- baseline 采样结果可复现
- QEMU 启动方式稳定

### 6.2 功能保持

- 目标模块功能 smoke 通过
- `debugfs` 仍可用
- `function_graph` 仍可用
- `perf` 仍可用

### 6.3 自动化

- baseline collect 能一键跑
- compare 能一键得出差异
- regression 能一键做基本验证

### 6.4 文档收口

- README 说明“做了什么”
- RESULTS/REPORT 说明“结果如何”
- records 里能找到原始证据

---

## 7. 我建议把 W3 理解成什么

一句话：

> W3 不是“内核裁剪那几天”，而是“把实验平台变成作品平台的准备阶段”。

W1/W2 让你有“能跑的驱动实验”；
W3 让你有“可重复、可对比、可回归的实验平台”；
W4/W5 则是在这个方法论之上，换一个更贴近岗位表达的 PCIe 作品主题继续往前走。

所以从整个仓库的学习逻辑看：

- W1/W2 是功能学习
- W3 是工程化收口
- W4/W5 是作品化表达

这样理解，整条线就会非常顺。
