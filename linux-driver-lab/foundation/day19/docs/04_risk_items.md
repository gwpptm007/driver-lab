# Day19 风险项

## 1. 为什么要把风险单独列出来

D19 的任务不是只给一个“看起来变小了”的表，而是要告诉后续自己：

- 哪些结论能直接讲
- 哪些结论讲的时候必须带限制条件
- 哪些地方以后最容易踩坑

所以风险项不能只写在表格备注里，必须单独沉淀。

---

## 2. 当前建议的风险分组

### 2.1 平台扩展风险

当前结论主要建立在：

- `arm64`
- `QEMU virt`
- 当前 demo 与 DT 注入路径

如果后续扩展到：

- PCIe
- virtio 更多变体
- 真板外设
- 更复杂的驱动链

那么今天被裁掉的某些配置，未来可能需要补回。

### 2.2 观测能力保留风险

W3 的目标不是做“极限最小镜像”，而是做“还能调、还能 trace、还能 perf 的最小实验平台”。

这意味着：

- `DEBUG_FS`
- `FTRACE`
- `FUNCTION_GRAPH_TRACER`
- `PERF_EVENTS`

这些能力不能轻易删。

风险就在于：

> 如果只盯着体积，很容易把真正有价值的观测能力一起裁掉。

### 2.3 口径不完全统一风险

D15 / D16 / D18 当前并不是同一套 records 风格：

- D15、D16 更偏文档结果
- D18 更偏标准化 records

因此：

- 某些字段在前两阶段缺省
- 某些字段在第三阶段非常完整
- Day19 这版只能先产出“草稿版对比”

### 2.4 rootfs 周期变化风险

D17 之后，rootfs 已进入“带 perf 工具”的新周期。

这会影响：

- `rootfs.img` 体积
- `boot_ms`
- `perf` 相关结论

所以：

> D18 的数字能进表，但不能无条件和 D15 / D16 做纯收益排名。

### 2.5 结论表达风险

D18 里有两层价值：

- 分类表达成立
- 当前 classified profile 也能跑通

但 Day19 表达时不能写成一句模糊的“D18 证明裁剪更好了”。

更准确的说法应该是：

- D18 更强地证明了“配置表达方式更清楚了”
- 至于“量化收益到底提升了多少”，必须回到同口径数据再说

---

## 3. 当前建议写进报告的风险摘要

Day19 报告正文里建议至少带上这几条：

1. 当前对比中，**D15 baseline 与 D16 round1** 的量化关系最稳。
2. **D18 classified** 可以作为当前最终阶段结果入表，但其 boot / rootfs / perf 已处于新周期，解释时必须带 caveat。
3. `module 数` 里，当前更稳的可读字段是 `modules_loaded_count`；`modules_built_count` 在 D15 / D16 尚未显式沉淀。
4. 以 `QEMU virt` 成立的裁剪结论，不自动等价于未来扩到更多平台时仍然可直接照搬。

---

## 4. 当前风险结论

Day19 这版最重要的不是把风险“消灭掉”，而是先把风险“写明白”。

这样后面无论是继续补统一 records，还是做 D21 总结报告，都不会把草稿版结论讲得太满。
