# Day19 计划稿（工程化结构版）

## 一、Day19 原始需求

**D19**  
任务：输出对比：`size / boot / mem / module 数`；列风险项  
产出/验收：**对比报告草稿**

这意味着 Day19 的核心不是继续做新的功能 bring-up，也不是再单独发起一轮没有边界的裁剪实验，而是把前面已经沉淀下来的阶段性结果，组织成一份可阅读、可复查、可继续增强的对比报告草稿。

---

## 二、Day19 的原始目标，翻译成现在这套工程里的真实含义

把 Day19 放到当前 `linux-driver-lab` 的上下文里，它的真实含义可以拆成两层。

### 2.1 对外的任务表达

对外必须仍然严格沿用 `W3_REVIEW.md` 的阶段定义：

- **D15 = baseline**
- **D16 = trim1**
- **D18 = trim2**

Day19 要做的，是把这三个阶段的关键指标放到同一张对比视图里，并给出风险说明。

### 2.2 对内的工程现实

结合当前最新代码，前序阶段的数据沉淀方式并不完全一致：

- `day15/` 更偏结果文档沉淀，例如 `RESULTS.md`
- `day16/` 同时保留了学习/分析/应用记录和结果文档，例如：
  - `RESULTS_ROUND1.md`
  - `RESULTS_ROUND2B.md`
  - `RESULTS_SUMMARY.md`
- `day18/` 已经进一步具备标准化 `records/compare/evidence` 风格

因此 Day19 在当前代码基线下的真实工作，不是“重新定义指标”，而是：

1. 找到 D15 / D16 / D18 已有结果
2. 统一字段口径
3. 生成对比表
4. 补上解释与风险项
5. 形成报告草稿

也就是说，Day19 的本质是：

> **把已有成果工程化收口。**

## 三、我建议的 Day19 定位

Day19 最合适的定位，不是“再做一轮裁剪主战场”，而是：

> **一个独立的、文档型工程目录，用来生成和沉淀 D15 / D16 / D18 的对比报告草稿。**

这里的关键词有三个：

### 3.1 独立

Day19 不继续把逻辑塞进 `day18/`，而是拥有自己的目录、文档、脚本和输出位置。

### 3.2 文档型工程

Day19 不是只放一篇 markdown，也不是只放一个临时表格，而是：

- 有入口说明
- 有计划文档
- 有后续脚本位
- 有 output / records 目录
- 有清晰的数据来源约束

### 3.3 报告草稿导向

Day19 的交付目标仍然很克制：

- 先形成 **对比报告草稿**
- 不急着做成过重的“报告平台”
- 不把范围扩展到 D20 的自动化回归

所以，Day19 的推荐定位可以概括为：

> **实现方式按工程做，交付目标按 D19 原始需求收敛。**

## 四、Day19 独立目录

Day19 仍然应该独立成目录，这不是形式问题，而是职责边界问题。

### 4.1 为什么不能继续混在 day18

如果把 Day19 的汇总逻辑继续放在 `day18/`，后面会出现两个混乱：

- 看不清哪些内容属于 Day18 自己的分类裁剪验证
- 看不清哪些内容属于 D19 的阶段对比结论

### 4.2 独立目录的直接好处

独立目录后，职责就很清楚：

- `day15/`：baseline 冻结与结果
- `day16/`：第一轮粗裁与结果
- `day18/`：第二轮分类裁剪与结果
- `day19/`：汇总、对比、解释、列风险、形成草稿

### 4.3 也更方便后续扩展

如果后面还要继续做：

- 补齐统一 records
- 自动重新生成报告
- 为 D20 / D21 输出交付说明服务

那 Day19 独立目录会比“在 day18 里夹一堆总结文件”更稳。

因此，Day19 目录的目标应当是：

> **一个有输入约束、有文档、有脚本位、有输出目录的独立目录。**

## 五、Day19 最推荐的数据来源方案

这一节要区分“对外口径”和“内部落地”。

### 5.1 对外口径：固定不变

Day19 对外始终按三阶段写：

- **baseline = D15**
- **trim1 = D16**
- **trim2 = D18**

这是原始任务定义，不能因为当前目录里某个 day 的 records 更完整，就把外部表达改掉。

### 5.2 内部取数原则：先复用已有沉淀

当前阶段最稳的取数方式是：

#### baseline（D15）
优先来源：
- `linux-driver-lab/day15/RESULTS.md`

可抽取信息示例：
- `Image` 大小
- `rootfs.img` 大小
- boot 相关结果
- `MemTotal / MemFree / Slab`
- 模块加载数量
- tracing / perf 相关状态说明

#### trim1（D16）
优先来源：
- `linux-driver-lab/day16/RESULTS_ROUND1.md`
- `linux-driver-lab/day16/RESULTS_SUMMARY.md`
- 必要时补充参考 `RESULTS_ROUND2B.md` 中对 round1/round2b 的对照解释

可抽取信息示例：
- 第一轮裁剪后的体积变化
- boot 与内存结果
- 模块数量变化
- 保留 tracing / perf 带来的取舍说明

#### trim2（D18）
优先来源：
- `linux-driver-lab/day18/records/compare-*.csv`
- `linux-driver-lab/day18/records/compare-*.md`
- `linux-driver-lab/day18/records/*/metrics.env`
- `linux-driver-lab/day18/records/*/baseline.csv`

可抽取信息示例：
- 第二轮分类裁剪后的量化结果
- 各 profile 对比结论
- 等价性检查结果
- 证据链与风险说明

### 5.3 推荐的落地顺序

最推荐的不是一开始就追求“绝对统一重采样”，而是：

> **先基于已有文档与 records 形成草稿版报告，再决定是否补统一重采样。**

这样做的原因很实际：

1. 更符合 D19 当前“报告草稿”的交付边界
2. 能尽快形成可读版本
3. 后面如果发现某些字段口径仍需统一，再做增强不会推翻前面的目录结构

## 八、Day19 的脚本设计建议

当前阶段还不直接写脚本，但计划里应该把脚本职责说清楚，避免后面边写边想。

### 8.1 `run_day19_report.sh` 的职责（计划）

建议后续让它承担这几件事：

1. 检查依赖文件是否存在
2. 检查 `output/` 与 `records/` 目录
3. 调用 `generate_day19_report.py`
4. 打印生成结果路径

这样它会成为 Day19 的统一入口。

### 8.2 `generate_day19_report.py` 的职责（计划）

建议后续让它完成四步：

#### A. 读取输入
从 D15 / D16 / D18 的结果文件中提取需要的指标。

#### B. 统一字段
把不同来源整理成统一结构，例如：

- `stage`
- `image_kib`
- `rootfs_kib`
- `boot_ms`
- `memtotal_kib`
- `memfree_kib`
- `memavailable_kib`
- `slab_kib`
- `modules_built_count`
- `modules_loaded_count`
- `function_graph_ok`
- `perf_ok`
- `notes`

#### C. 输出对比表
生成：

- `output/day19_compare_table.csv`

#### D. 输出草稿报告
生成：

- `output/day19_compare_report_draft.md`

### 8.3 `source_manifest.csv` 的职责（计划）

建议后续加入一个显式的数据来源声明文件，用来记录：

- 某个阶段使用了哪个来源文件
- 某个字段是直接抽取还是人工整理
- 哪些结论来自结果文档，哪些来自标准化 records

这样可以避免 Day19 变成“脚本硬编码黑箱”。

### 8.4 脚本实现风格建议

Day19 的脚本不追求复杂，而追求：

- 路径清楚
- 字段命名统一
- 对输入缺失有清晰提示
- 输出结果人眼可读
- 便于后续增强

## 九、Day19 报告里必须有的内容

Day19 最终的报告草稿，不能只是贴一张表。至少应当包含以下部分。

### 9.1 背景说明

要说明：

- D19 的原始任务是什么
- 为什么要做三阶段对比
- D15 / D16 / D18 分别代表什么

### 9.2 数据来源说明

要说明：

- baseline 数据来自哪里
- trim1 数据来自哪里
- trim2 数据来自哪里
- 当前是否存在“文档结果 + records 混合取数”的情况

### 9.3 关键指标对比表

建议至少包含：

- `Image`
- `rootfs.img`
- boot time
- `MemTotal`
- `MemFree`
- `MemAvailable`
- `Slab`
- 构建模块数
- guest 实际加载模块数
- `function_graph` 是否可用
- `perf` 是否可用
- 风险备注

### 9.4 关键变化解读

不能只给数字，还要说明：

- 哪一轮体积下降明显
- boot 是否有明显收益
- mem 指标是否支持“裁剪确实有收益”
- module 数变化说明了什么

### 9.5 风险项

风险项要单独成节，而不是藏在表格最右侧一小列里。这样后面才方便沿用和扩展。

### 9.6 当前结论

要明确写清楚：

- 哪些结论已经比较稳
- 哪些仍然是草稿版判断
- 哪些后续需要靠统一重采样进一步确认

## 十、Day19 的风险矩阵我建议先沉淀这几类

Day19 的风险矩阵建议先从以下几类开始沉淀。

### 10.1 平台扩展风险

当前结论主要在 `QEMU virt + arm64` 场景下成立。后续如果扩展到：

- PCIe
- 更多 virtio 变体
- 真板外设

某些当前裁掉的配置项，可能需要补回。

### 10.2 观测能力保留风险

为了保留：

- debugfs
- tracing
- function_graph
- perf

某些配置就不能做极限裁剪。所以“镜像没有裁到最小”未必是失败，而是为了保留分析能力所做的取舍。

### 10.3 对比口径风险

如果 D15 / D16 / D18 三阶段的：

- rootfs
- 启动参数
- 采样脚本
- 模块版本
- 统计口径

并不完全一致，那么 Day19 的对比结论就必须以“草稿版”口径表达，不能过度下最终结论。

### 10.4 实现路径风险

当前 BusyBox 路线是最稳的实验路径，但后续如果需要更强 rootfs 扩展能力，可能还要讨论 Buildroot 或其他方式。

### 10.5 结论表达风险

D18 更偏“分类表达成立”和“等价性说明”；而 D19 要表达的是“阶段收益对比”。

这两件事不能在报告里混写成：

- “都证明了裁剪成功”

更准确的表达应该是：

- D18 提供了分类方法的解释能力
- D19 输出的是跨阶段量化对比与风险总结

## 十二、学习角度上，Day19 你会真正学到什么

Day19 虽然不像前面的某些 day 那样直接围绕驱动代码、trace 或 perf 操作展开，但它训练的是非常重要的工程收口能力。

### 12.1 如何做统一口径

不是只记“某一轮变小了”，而是把多个阶段的数据统一成同一组字段，这种能力在真实项目里非常常见。

### 12.2 如何做量化结论

不是停留在“感觉优化了”，而是明确：

- 哪个指标变了
- 变了多少
- 这能不能写进结论

### 12.3 如何把技术过程沉淀成可复查资料

这对以后你做：

- sandbox 性能/资源分析
- 内核裁剪汇报
- 项目验收
- 面试项目表达

都会很有帮助。

### 12.4 如何区分“方法成立”和“收益成立”

这是 Day19 特别值得学的一点：

- 某个方法可解释、可复用，不等于它已经完成跨阶段收益证明
- 某个结果看起来变好了，也不等于方法论已经沉淀完整

Day19 的写法，正好训练你把这两者拆开表达。
