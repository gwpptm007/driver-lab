本次 Day09 的目标是验证下面这条链路是否真正打通：

## 3. 问题一：模块编译失败，`of_device_get_match_data` 报隐式声明

### 3.1 现象

执行 `./build.sh` 时，模块编译阶段报错，核心信息类似：

```text
error: implicit declaration of function ‘of_device_get_match_data’
warning: assignment to ‘const char *’ from ‘int’ makes pointer from integer without a cast
```

报错位置在 `demo_of.c` 中：

```c
priv->match_name = of_device_get_match_data(dev);
```

### 3.2 原因分析

这不是 arm64 环境没准备好，也不是 DT 片段的问题，而是 **当前 Linux 5.15.10 环境下接口兼容性问题**。

本代码只是想从 `of_match_table` 的 `.data` 字段里取到：

- `"day09-of-match"`

对于当前这套 5.15.10 构建环境，使用更通用的：

- `device_get_match_data(dev)`

更稳定，也更适合作为本实验的写法。

### 3.3 解决方法

把：

```c
priv->match_name = of_device_get_match_data(dev);
```

改成：

```c
priv->match_name = (const char *)device_get_match_data(dev);
```

### 3.4 结论

修改后，模块可以顺利编译，说明：

- arm64 内核构建目录有效
- 外部模块交叉编译链路有效
- day09 的第一版驱动代码可继续进入运行阶段

## 4. 问题二：`reg` 解析成功，但 `platform_get_irq()` 失败

### 4.1 第一次运行现象

QEMU 启动进入 guest 后，执行：

```sh
insmod /demo_of.ko
dmesg | grep demo_of
```

日志显示：

- `probe start`
- `raw DT reg cells` 正常
- `parsed MEM resource` 正常
- `raw DT interrupts cells` 也能看到
- 但是 `platform_get_irq()` 失败

关键现象类似：

```text
raw DT interrupts cells: <0x0 0x2a 0x4>
parsed MEM resource: start=0x10000000 end=0x10000fff size=0x1000
irq: type mismatch, failed to map hwirq-74 for intc@8000000!
IRQ index 0 not found
platform_get_irq failed: -6
```

### 4.2 先确认哪些已经成功

这一步其实已经说明下面这些都成功了：

- DT 节点已经进入系统
- `compatible` 已经匹配成功
- `probe()` 已经执行
- `reg` 已经成功解析

所以问题已经缩小到了：

- **IRQ 映射失败**

### 4.3 原因分析

原来的 DT 片段里写的是：

```dts
interrupts = <0x0 0x2a 0x4>;
```

也就是：

- SPI 中断号 `0x2a`（42）
- 触发类型 `0x4`

在当前这台 QEMU `virt` 机器上，这个中断号对应的映射不合适，和现有 GIC 中断布局发生了冲突，所以会出现：

- `type mismatch`
- `failed to map hwirq-74`

这里的 `74` 可以理解为 GIC 映射后的硬件中断号，不是说 DT 没读到，而是 **这个 IRQ 号本身不适合作为我们这个教学节点使用**。

### 4.4 解决方法

把 `demo_day09.fragment.dtsi` 中的：

```dts
interrupts = <0x0 0x2a 0x4>;
```

改成：

```dts
interrupts = <0x0 0x64 0x4>;
```

也就是把中断号从：

- 42

改成：

- 100

这个值在当前实验里更适合作为一个“可成功映射的测试 IRQ”。

### 4.5 修改后的结果

重新执行 `./build.sh`，进入 guest 后再次 `insmod /demo_of.ko`，日志变成：

```text
probe start
of node full name: demo_dt@10000000
of match data: day09-of-match
dt label: from-qemu-dt
raw DT reg cells: <0x0 0x10000000 0x0 0x1000>
raw DT interrupts cells: <0x0 0x64 0x4>
parsed MEM resource: start=0x10000000 end=0x10000fff size=0x1000
parsed Linux IRQ: 49
```

这说明：

- DT 中的 `interrupts` 已经被正确解析
- `platform_get_irq()` 已经成功
- day09 的 `irq` 解析链路打通了

## 6. 这次测试的学习收获

### 6.1 `reg` 和 `interrupts` 的调试要分开看

即使 `reg` 已经成功，也不代表 `irq` 一定成功。

本次就是：

- `reg` 成功
- `irq` 失败

所以调试时要分开判断。

### 6.2 `probe()` 能进，不代表所有资源都已正确映射

本次第一次运行时：

- `probe()` 已经进了
- `reg` 也拿到了
- 但 `platform_get_irq()` 仍然失败

这说明：

- 匹配成功
- 不等于所有资源都没问题

### 6.3 DT 原始 cells 和驱动最终拿到的资源，是两层概念

日志里同时打印：

- `raw DT reg cells`
- `raw DT interrupts cells`
- `parsed MEM resource`
- `parsed Linux IRQ`

这非常有助于理解：

- 设备树里原始写了什么
- 内核最后交给驱动的资源是什么

这也是 Day09 这节课最有价值的观察点之一。
