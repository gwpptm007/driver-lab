# Day21 报告结构设计

## 1. 为什么要单独设计结构

Day21 的目标不是“把所有内容缩短一点”，而是“把真正重要的内容按最容易讲清楚的顺序重新组织”。

如果结构不先设计好，很容易出现两种问题：

- 1-2 页里塞满细节，看起来像拼贴摘要
- 只剩结论，没有方法和边界，读者不信

所以 Day21 必须先设计结构，再写正文。

## 2. 推荐结构

我建议 Day21 的正式报告采用下面 5 段结构：

### 第一段：背景
一句话交代 W3 目标，再补两三句当前环境现状与为什么需要收敛。

### 第二段：方法
用最简洁的方式把 D15-D20 串起来：
- baseline
- trim1
- trim2
- compare
- regression

### 第三段：核心数据
给一张核心对比表，只保留真正高价值字段：
- Image
- rootfs.img
- boot
- mem
- module 数
- tracing/perf 状态（如果需要）

### 第四段：结论
把最重要的判断写出来：
- 收益有没有
- 保留能力有没有丢
- 当前最推荐配置是什么
- 哪些结论带边界

### 第五段：回滚方案
单独列出来，不要藏在最后一句话里。

## 3. 为什么不建议再拆更多段

因为 Day21 的限制就是 1-2 页。

如果再拆成：
- 详细风险
- 详细工具链
- 详细脚本说明
- 详细问题列表

篇幅会立刻失控，这些内容更适合保留在 Day19 / Day20。

## 4. 每一段的写法建议

### 背景
控制在 4-6 行。

### 方法
控制在 5-8 行，最好用阶段串联，不要展开函数级细节。

### 数据
一张表 + 2-4 行解释就够。

### 结论
尽量写成判断句，而不是口号句。

### 回滚方案
写成操作路径，而不是抽象建议。

## 5. 输出形式建议

后面正式产物建议至少保留两版：

### 1）正式版
- `output/day21_report_final.md`

### 2）更压缩的一页版
- `output/day21_report_onepager.md`

这样既方便完整交付，也方便快速讲解。
