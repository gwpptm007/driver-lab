# day31 设计与风险

## 1. 设计原则

### 原则 1：尽量少改驱动，尽量把 bench 逻辑放在用户态

Day31 的核心价值是“量化”，而不是把驱动做得越来越大。

因此当前策略是：

- 驱动只保留必要的 `mmap / ioctl / DMA / 最小统计`
- 计时、分位数、CPU 占用统计放在 guest bench tool 里完成

### 原则 2：路径定义必须固定

如果不先定义“单次操作是什么”，所有统计都很容易失真。

所以当前已经把 `bench-ioctl / bench-mmap / bench-dma` 三种模式写死成清晰的动作序列。

## 2. 当前边界

- `mmap` 仍然只支持整页映射 + `offset=0`
- DMA buffer 布局仍沿用 day30：`src_off=0`、`dst_off=2048`
- 默认 payload 仍建议不超过 `2048`

## 3. 风险点

### 风险 1：guest 虚拟环境中的绝对数值不宜过度泛化

Day31 的结果更适合：

- 比较相对差异
- 比较路径之间的级别关系
- 比较不同 payload 的趋势

不太适合直接宣称“这就是某类真实硬件的最终性能”。

### 风险 2：iterations 太小会导致 p99 不稳定

如果要更认真分析尾延迟，应该增加样本量。

### 风险 3：DMA 路径的 bench 更容易受虚拟化调度影响

因此 Day31 文档里要强调：

- 结果主要用于本学习工程内的相对比较
- 不要过度外推
