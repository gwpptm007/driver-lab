# 04_RETEST_20260607 — Phase 2 重新测试

## 为什么要重新测试

上次测试（2026-05-10）PASS_SOCKET_READY 和 PASS_UMEM_RINGS 都通过了，但 `PASS_RX_TRAFFIC` 未通过——`rx_packets=0`。缺乏 RX 流量意味着 AF_XDP socket + XDP redirect + UMEM + ring 的完整数据闭环没有被真正验证。

本次目标：在 AF_XDP socket 的 RX ring 中收到非零数据包。

## 上次为什么 rx_packets=0

原因和 Phase 1 完全相同：**同主机发包到本地 IP 走 local delivery 短路，XDP hook 不触发。**

```text
ens33 (192.168.100.77) → UDP → 192.168.100.1 (ens192)
    → 内核路由发现目标 IP 是本地
    → 走 local delivery，不经过 ens192 RX 路径
    → XDP 程序不执行
    → bpf_redirect_map 不调用
    → AF_XDP socket RX ring 为空
```

上次测试的日志也印证了这一点：`rx_empty_polls=147`（15 秒内 147 次 poll 返回空），说明 AF_XDP 初始化完全正常，只是没有包到达 XDP hook。

## 本次解决方案：veth pair

和 Phase 1 完全相同的方案——用 veth pair 替代物理网卡，从 veth-peer 端注入流量，veth-xdp 端挂 XDP + AF_XDP socket。

```text
veth-peer (10.99.0.2)  ──→  veth-xdp (XDP + AF_XDP socket)
   ping -I veth-peer            XDP: bpf_redirect_map(xsks_map, queue=0)
                                AF_XDP socket: UMEM RX ring ← 包到达这里
                                用户态: xsk_ring_cons__peek() 取出
```

**为什么 AF_XDP on veth 能工作？**

AF_XDP 的核心依赖不是物理 DMA，而是：
1. XDP 程序能 attach 到网卡 → veth 5.4+ 支持 XDP
2. XDP 程序能通过 XSKMAP redirect 到 socket → 纯内核机制，与网卡无关
3. UMEM 是用户态内存 → 与网卡无关
4. `XDP_COPY` 模式：内核把包内容 copy 到 UMEM → 不依赖网卡 DMA

当前应用使用 `XDP_COPY` 模式（`--copy` 参数），所以即使在 veth 上也完全可用。如果是 `XDP_ZEROCOPY` 模式则需要网卡 DMA 支持，vmxnet3 不支持。

## 两轮流量差异的原因

| 维度 | 首轮 | 脚本轮 |
|------|------|--------|
| 运行时长 | 15s | 12s |
| 流量注入 | 100 次 ping | 80 次 ping |
| 流量与 poll 窗口重叠 | 刚好 | 稍偏 |
| rx_packets | 49 | 3 |

脚本轮 ping 启动略有延迟，大部分 ping 落在了 app 的 `rx_empty_polls` 周期而不是 RX ring 活跃期。ARPP 请求首先被 XDP redirect 到 socket，但 ping 没有收到 ARP reply 后就不发了。不管 rx_packets 是 3 还是 49，PASS_RX_TRAFFIC 的条件（>0）都已满足。

## 知识点总结

### 1. AF_XDP 数据路径的四个阶段

| 阶段 | 触发者 | 关键操作 |
|------|--------|----------|
| 初始化 | 用户态 | UMEM 分配 → socket 创建 → ring 设置 → XDP attach → XSKMAP 注册 |
| 收包 | 内核 | XDP hook → bpf_redirect_map → 写 RX ring descriptor |
| 消费 | 用户态 | poll → xsk_ring_cons__peek → 读 UMEM → 统计 → 回收 frame |
| 清理 | 用户态 | detach XDP → 删除 socket → 释放 UMEM |

### 2. XDP_COPY vs XDP_ZEROCOPY 在 veth 上的表现

veth 没有 DMA 引擎，所以 `XDP_ZEROCOPY` 不可用。但 `XDP_COPY` 完全可用——内核把包内容从 skb 拷贝到 UMEM frame。这对功能验证来说足够，只是多一次内存拷贝。

### 3. fill_recycled 的含义

`fill_recycled` 表示"从 RX ring 取出后重新放回 FILL ring 的 frame 数量"。在正常收包流程中它应该等于 rx_packets：

```
收包: 内核从 FILL ring 取 frame → 写入 RX ring
消费: 用户态从 RX ring 取 frame → 读数据 → 放回 FILL ring (fill_recycled++)
```

首轮测试中 `fill_recycled=49 = rx_packets=49`，证明回收逻辑正确。

### 4. veth 是 AF_XDP 开发测试的标准工具

AF_XDP 的所有核心机制（UMEM、ring、XSKMAP redirect）都与网卡硬件无关（在 COPY 模式下），因此 veth pair 完全可以作为开发测试环境。这在 Linux 内核自带的 AF_XDP selftest（`tools/testing/selftests/bpf/xsk.c`）中也是用 veth 做的。
