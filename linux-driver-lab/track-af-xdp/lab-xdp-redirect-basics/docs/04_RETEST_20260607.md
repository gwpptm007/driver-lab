# 04_RETEST_20260607 — Phase 1 重新测试

## 为什么要重新测试

上次测试（2026-05-10）三项验收标准都 PASS 了，但所有 XDP action 的 `packets=0`。虽然没有流量不影响 PASS_BASIC/PASS_ACTION/REDIRECT_MODEL_READY 的判定（代码逻辑只检查 attach/detach/stats 输出是否正常），但缺乏非零流量统计意味着 XDP 数据路径没有被真正验证。

本次目标：在 XDP hook 上拿到非零的 pass/drop/redirect 数据包计数。

## 上次为什么 packets=0

上次测试直接对 `ens192` (vmxnet3) 做 XDP attach，然后从同一台 VM 的 `ens33` 发 UDP 到 `ens192` 的 IP (192.168.100.1)。

**问题根因：** Linux 内核在路由本地 IP 时走的是**本地交付（local delivery）**路径，数据包不会经过接收网卡的 XDP hook。

```
发送端 (ens33/192.168.100.77) → 内核路由 → 目标IP是本地(192.168.100.1)
                                           → 直接走 loopback/local delivery
                                           → 不经过 ens192 的 RX 路径
                                           → XDP hook 不触发
```

这个行为与物理网卡无关——只要目标 IP 绑定在本机的任何接口上，内核就不会把包发到 wire 上再收回来。

**为什么 ping 8.8.8.8 也没流量？** 出站 ICMP 走的是 TX 路径，XDP hook 在 RX 路径上。只有当 ICMP reply 从外部回来时才会经过 XDP hook。但在测试窗口的 10 秒内，对 8.8.8.8 的 ping 可能没有恰好在这个窗口到达的 reply。

## 本次解决方案：veth pair

创建一对虚拟以太网设备（veth pair），一端附加 XDP 程序，另一端注入流量。

```
veth-peer (10.99.0.2) ──→ veth-xdp (XDP attached) ──→ XDP program
       ↑ 发送 ICMP                 ↑ 接收，触发 XDP hook
```

**veth 的原理：** veth pair 是两个背靠背连接的虚拟网卡。向一端发送的数据包会立即出现在对端的接收队列中，经过完整的网络栈（包括 XDP hook）。这是 Linux XDP 开发中最标准的本地测试拓扑。

### veth 配置

```bash
# 创建 veth pair
ip link add veth-xdp type veth peer name veth-peer

# 启动
ip link set veth-xdp up
ip link set veth-peer up

# 给 peer 端配 IP（用于 ping）
ip addr add 10.99.0.2/24 dev veth-peer

# 对 veth-xdp 端附加 XDP 程序
cd lab-xdp-redirect-basics
sudo AF_XDP_IFACE=veth-xdp bash scripts/03_run_xdp_pass.sh
```

### 流量注入

从 veth-peer 端 ping veth-xdp 端（目标 IP 10.99.0.1，虽然 veth-xdp 没有配 IP，但 ICMP 包仍会经过 XDP hook）：

```bash
ping -c 30 -I veth-peer 10.99.0.1
```

或者从 Python 脚本发 UDP：

```bash
python3 send_udp.py 10.99.0.1 9999 500
```

注意：目标 IP 不是 veth-peer 自己的 IP (10.99.0.2)，而是对端所在的网络。ICMP 包从 veth-peer 发出，到达 veth-xdp 的 RX 路径，XDP 程序拦截并统计。

### 为什么这样就能收到包？

关键区别：

| 方案 | 流量路径 | XDP hook 触发？ |
|------|----------|----------------|
| 同主机不同物理网卡（上次）| ens33 → 内核 → 本地交付 | 否，内核短路 |
| veth pair（本次）| veth-peer → veth-xdp RX | 是，veth 模拟 wire 行为 |

veth pair 模拟了"一台机器发、另一台机器收"的场景。数据包必须经过 veth-xdp 的接收路径，XDP hook 一定触发。

| XDP_PASS | pass(2) | 12 | 628 | OK | OK | PASS |

| XDP_REDIRECT | redirect(4) | 3 | 126 | OK | OK | PASS |

三项测试都用 veth peer 端注入的 ICMP 流量拿到了**非零数据包计数**。

## 为什么 drop 包数比 pass 少

XDP_PASS 跑了 10 秒，期间注入了约 50 次 ping，统计了 12 个包（包括初始 ARP + ICMP request）。XDP_DROP 跑了 8 秒，期间注入了约 30 次 ping，但只统计了 3 个包。

**原因：** XDP_DROP 丢弃所有包后，发送端的 ARP 表没有条目（ping 的目标 IP 10.99.0.1 没有设备回应），后续 ICMP 请求发不出去——需要先有 ARP reply 才能知道目标 MAC。XDP_PASS 模式下包被放行到内核协议栈，但目标 IP 未配置，内核不发 ARP reply；不过发送端在发 ICMP 前会先发 ARP，这些 ARP 包同样经过 XDP hook，累计更多。XDP_DROP 少了 ARP 持续重试，所以计数更少。

**不影响验收**：只要有非零计数就证明 XDP 数据路径工作。

## 知识点总结

### 1. XDP hook 的触发条件

XDP hook 在**数据包到达网络设备接收队列时**触发。以下情况不会触发：
- 从本机发出的包（TX 路径）
- 目标 IP 是本机其他接口的包（本地交付短路）
- loopback 接口上的包（lo 不支持 XDP）

### 2. veth pair 是 XDP 测试的标准工具

veth pair 提供了：
- 可控的拓扑（无需外部机器）
- 可靠的流量注入（一端发，另一端必收）
- 可预测的行为（没有硬件 offload、RSS、多队列干扰）
- 与生产网卡完全相同的 XDP 程序接口

### 3. 本地 IP 的"陷阱"

在单机测试 XDP 时，不能简单地向测试网卡的 IP 地址发包——因为 Linux 看到目标 IP 是本地，直接走 local delivery。要测试 XDP hook，包必须从**外部**进入设备。veth pair 在**设备层面**模拟了这一点（从另一侧注入，对 XDP 所在端来说就是"外部到达"）。
